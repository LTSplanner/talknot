# 修正・新機能の出し方（先行確認 → 全体公開）

プランナー8名が毎日使うツールなので、**いきなり全員に出さない**。
まず先行公開の対象者（既定：`hkumada@life-time-support.com`）で確かめ、
問題なければ全員に出す。対象者は `.env` の `CANARY_EMAILS` で変更できる。

変更の種類によって「先行公開のやり方」が変わるので、下の3つに当てはめて進める。

---

## A. 画面に出る機能（タブ・ボタン・新しい表示）

**機能フラグを使う。** コードは本番に入れてよいが、既定OFFにしておけば
プランナーの画面は変わらない。

1. `config/settings.py` にフラグを足す（**既定 OFF**）

   ```python
   FEATURE_XXX = _bool_env("FEATURE_XXX", False)
   _FEATURE_FLAGS = { ..., "xxx": FEATURE_XXX }
   ```

2. 画面側で出し分ける

   ```python
   if settings.feature_visible("xxx", user.get("email")):
       render_xxx(user)
   ```

   これで **先行公開の対象者と管理者にだけ見える**。プランナーには出ない。

3. 対象者に見てもらう → 問題なければ `.env` / Streamlit Secrets で
   `FEATURE_XXX=true`（または既定値を True に変更して push）
4. 全員に公開されたら、フラグと出し分けを消して普通のコードに戻す

---

## B. 評価の中身（プロンプト・称号・スコアの出し方）

画面ではなく **出力の質** が変わるもの。フラグでは隠せないので、
**先に対象者の実データで1件だけ動かして確かめる**。

1. 変更をローカルに入れる（push しない）
2. 対象者の録画・ロープレを1件だけ評価して、出力を目視する
   - 商談：`scripts/auto_evaluate_meetings.py` を上限1件で実行、または
     対象の1件だけを指定して実行する
   - 文字数・件数・固有名詞・「次の一言」がセリフになっているか を必ず見る
3. 問題なければ commit → push（次の自動実行から全員に効く）

> 過去の評価はさかのぼって書き換わらない。称号は履歴から毎回計算するので、
> 称号の追加・変更だけは**過去の実績にさかのぼって反映される**。

---

## C. 通知（Chat リマインド）

**対象者へ1通だけ実際に送って確かめる。** 文面は届いてはじめて印象が分かる。

1. 変更をローカルに入れる
2. `--dry-run` で対象者・本文・件数を確認（送信されない）
3. 対象者にだけ1通送って、実物を見てもらう
4. 問題なければ commit → push（次の定期実行から全員に届く）

---

## 共通のルール

- **push＝全員公開**。Streamlit Cloud は main を見ているので、
  push した時点でプランナーの画面が変わる。フラグOFFのコードだけが例外。
- **テストを必ず通す**（`pytest`）。判定ロジック・文面の条件はテストで固定してある。
- **消す変更は先に中身を見る**。評価履歴の削除など戻せない操作は、
  対象を一覧で出して確認してから実行し、可能ならバックアップを取る。
- **定期実行は GitHub 側で 1.4〜3.2 時間遅れる**。時刻の変更はこの遅延込みで考える
  （`auto-evaluate` は 10:20 UTC、`roleplay-reminder` は 03:40 UTC 指定）。
